# Промпт: Shelter Engine — визуальный редактор на Three.js без написания кода

Подготовлено 28 сентября 2026 года. Основа — официальная документация Epic для **UE 5.6**, одной из версий UE5, и текущая реализация проекта. Документ описывает будущее развитие; перечисленные новые возможности ещё не реализованы.

## Выбранный объём

**Главный приоритет пользователя: движок не зависит от конкретной игры.** Пользователь запускает движок, открывает существующий или создаёт новый проект, работает с ним в редакторе и выпускает самостоятельную сборку выбранной игры.

**Главное уточнение о роли ИИ:** ИИ выступает разработчиком — сначала определяет существующий движок/графическую библиотеку проекта и работает на этой основе. В текущем проекте подтверждены Three.js, TypeScript и Vite. **Сам редактор предназначен человеку для ручной расстановки объектов и корректировки игры без написания кода. Целевая сборка — только Web.** Форма запуска вторична по отношению к удобству визуальной работы.

Подтверждённый объём:

1. Рабочее пространство по принципам UE5, работа со сценой и запуск игры внутри редактора.
2. Полноценное визуальное создание игровой планировки с обновлением геометрии, проходов, обзора и маршрутов.
3. Импорт собственных статических GLB/glTF-моделей и текстур.
4. Управление независимыми проектами, расширяемая игровая логика и сборка выбранного проекта.
5. Перенос While the light is on в отдельный игровой проект и проверка движка на другом, независимом проекте.
6. Полный ручной рабочий процесс через графический интерфейс: размещение, свойства, готовые игровые настройки, проверка, сохранение и сборка без редактирования исходников, JSON или команд терминала.
7. Собственная общая библиотека 3D-моделей, текстур и материалов по принципу Fab: стартовый контент, каталог с превью, пополнение и добавление ресурсов в любой проект через интерфейс.

Базовый вариант реализации — веб-интерфейс редактора поверх существующего Three.js и локальная служба на Node.js для проектов в папках и Web-сборки. Обеспечь простой запуск редактора и далее весь рабочий процесс через его окна и кнопки. Собственный рендер с нуля, замена Three.js, обязательное управление через CLI/MCP, установщик настольного редактора и сборки игр для Windows/macOS в текущий объём не входят. Внутренние API и автоматические тесты остаются средствами разработки.

## Готовый промпт

На основе текущего кода реализуй **Shelter Engine — самостоятельную визуальную среду редактирования игр поверх существующего Three.js**, с рабочим пространством по принципам Unreal Engine 5. Основной пользовательский путь: **запустить редактор → создать или открыть проект → вручную собрать и скорректировать сцены → настроить готовые игровые возможности → проверить игру → выпустить самостоятельную Web-сборку**. Весь этот путь доступен в интерфейсе без написания кода.

**Независимость движка от конкретной игры — главное архитектурное требование.** While the light is on должна стать обычным проектом, использующим публичные возможности движка. Создание другой игры не требует редактировать исходники ядра, интерфейса редактора или системы сборки. Поддержка 2.5D является возможностью движка, а правила конкретной игры принадлежат её проекту.

**Роль ИИ — исследовать и разрабатывать проект на его текущей технической основе. Роль пользователя — вручную расставлять и настраивать игру через редактор.** Для обычной расстановки и правок пользователь не пишет TypeScript, не редактирует JSON, не вводит технические ID и не вызывает команды терминала. Возможность выполнить операцию только через API не считается реализацией этой функции редактора.

### 1. Контекст и сохранение текущей работы

Сначала изучи `GDD.md`, `README.md`, `docs/engine/EDITOR.md`, `docs/base/RENDERING-3D.md`, зависимости и точки запуска. Определи фактически используемые движок/библиотеку, рендерер, систему сцен, игровые модули и существующие инструменты редактора. Если основа уже есть, работай на ней и переиспользуй её возможности. Уточняй у пользователя выбор новой основы только при её отсутствии или выявленной несовместимости, которую нельзя разумно устранить в текущем стеке. Перед изменениями проверь рабочее дерево: в нём могут быть важные незакоммиченные изменения пользователя.

В текущем проекте проверено: в `package.json` есть зависимость `three`; `src/base/renderer-3d.ts` использует Three.js для 3D-сцены; `src/editor/scene-editor.ts` уже использует `OrbitControls` и `TransformControls`. Игровая логика реализована собственным TypeScript-кодом, сборка — через Vite. Three.js является графической основой, а создаваемый Shelter Engine добавляет переиспользуемые инструменты проектов, визуального редактирования и сборки. Продолжай на этой основе, используя готовые средства Three.js там, где они подходят.

Сделай локальную службу на Node.js для файлов проектов и сборки, веб-интерфейс редактора и отдельную точку входа игрового runtime. Служба нужна автору игры; в Web-билд она не входит. Старый `?editor` можно оставить совместимым переходом к редактору, но редактор должен запускаться самостоятельно, без предварительного запуска игры.

Опорные модули:

- `src/engine/scene.ts` — документ сцены, валидация, сериализация и история.
- `src/engine/scene-commands.ts` — операции над объектами и группами.
- `src/engine/runtime.ts` — создание объектов и применение сцены к игре.
- `src/editor/scene-editor.ts`, `selection.ts`, `camera-panel.ts`, `style.css` — существующий редактор.
- `src/game.ts`, `src/base/world.ts`, `input.ts`, `ui.ts`, `renderer-3d.ts` — игровой запуск, симуляция, ввод, интерфейс и рендер.
- `src/base/level.ts`, `config.ts`, `dimensions.ts` — игровая планировка и перевод координат.
- `tests/base/editor.test.ts`, `editor.spec.ts` и остальные проверки игровых механик.

Используй уже работающие выбор лучом и рамкой, множественное выделение, группы, TransformControls, мировые/локальные оси, размеры моделей, общие материалы, изоляцию, свет, текстуры, камеру, undo/redo и импорт/экспорт. Развивай их без потери поведения.

В перенесённой While the light is on сохрани объёмное окружение, плоского героя, движение по этажам/лестницам, игровую камеру по −Z, слежение и рост героя 1,78 м. Эти параметры должны храниться в проекте/его шаблоне. Другой проект может иметь другую камеру, персонажей, управление и игровые правила. Общие единицы движка — метры и градусы; преобразования старых координат остаются в адаптере миграции текущей игры.

### 1.1. Границы движка и игрового проекта

Раздели ответственность:

- **Ядро/runtime:** документы и сущности сцены, компоненты, трансформации, загрузка ресурсов, рендер, камеры, свет, аудио, действия ввода, жизненный цикл симуляции и API сохранений.
- **Редактор:** стартовый экран проектов, окна сцены, инспекторы, история, библиотека ресурсов, инструменты уровней и управление пробным запуском. Работает через публичные контракты ядра.
- **Инструменты:** импорт ресурсов, миграции, валидация, компиляция проектного кода и сборка под выбранную платформу.
- **Модули и шаблоны:** повторно используемые возможности, в том числе 2.5D-планировка. Подключаются проектом явно.
- **Игровой проект:** сцены, ресурсы, префабы, настройки, интерфейс игры, правила и код конкретной игры.
- **Оболочка движка:** доступ к файлам, диалоги и запуск сборки через ограниченные интерфейсы сервисов; её API не попадает в поставляемую игру.
- **Внутренние команды:** общий слой операций для интерфейса, истории, валидации и тестов. Пользователю не требуется работать с этим API напрямую.

Допустимо начать с одного репозитория и отдельных пакетов/директорий, но проект должен открываться из другого расположения без копирования исходников движка. Направление зависимостей: игра использует SDK движка; ядро и редактор не импортируют игру.

Устрани проверенные привязки текущего кода: импорты `BaseWorld`, `BaseAssets`, `BaseObject`, `ThreeRenderer` из `src/base` в движке/редакторе; обязательный `template: 'shelter-house-v1'`; фиксированные `PREFABS`; ссылки только вида `house/...`; обязательный фонарик героя; единственные глобальные ключи хранения; путь `/While-the-light-is-on/` в общей сборке. Общие части рендера выдели в движок, а игровые эффекты и правила подключай модулем проекта.

Введи версионированный контракт модулей и реестр типов компонентов/ресурсов для разработчиков. Проектный модуль регистрирует поведение и схему его настраиваемых свойств. По этим схемам редактор показывает человеку понятные поля, переключатели и выбор связанных объектов/ресурсов. Поддержи жизненный цикл загрузки, обновления, паузы и освобождения. Сборка компилирует проектный код вместе с нужным runtime; для обычной настройки игры пользователь не меняет этот код и центральный список типов движка.

Готовые поведения и параметры проекта доступны через инспектор. Создание нового поведения, которого ещё нет в модулях, остаётся задачей ИИ/разработчика на TypeScript; после его реализации пользователь настраивает его в редакторе. Не обещай создание любой произвольной механики без программирования: обязательный результат — ручная сборка сцен и корректировка поддерживаемых игровых возможностей без кода. Blueprint-подобный граф не требуется. Сцена хранит проверяемые данные и ссылки на модули, а не исполняемый текст.

### 1.2. Запуск, открытие и создание проектов

При запуске показывай **Менеджер проектов**: «Создать», «Открыть», «Недавние». Список недавних — только указатель; проект можно открыть без предварительной регистрации. Отсутствующий или перенесённый проект предлагает выбрать новое расположение. Запуск движка не загружает дом, героя и ресурсы текущей игры.

Создание проекта: имя, расположение/хранилище, шаблон, стартовая сцена и настройки сборки. Минимальные шаблоны — **Пустой 3D-проект** с камерой и **Нейтральный 2.5D-проект** с простыми геометрическими ресурсами и демонстрационным управлением. While the light is on доступна отдельно как перенесённый проект/пример, а не скрытая обязательная основа каждого шаблона.

Открытый проект содержит несколько сцен; можно создать, переименовать, дублировать, открыть сцену и назначить стартовую сцену игры. Редактор показывает название проекта и текущей сцены. Добавь «Настройки проекта», «Закрыть проект» и переход к менеджеру. При переключении предложи сохранить изменения, отказаться от них или отменить переход. Сбой открытия нового проекта не уничтожает текущий.

Закрытие проекта освобождает его сцены, runtime, библиотеки ресурсов, обработчики и рабочее состояние. История, выделение, черновики и игровой прогресс не переносятся в другой проект.

### 1.3. Формат проекта и данные

Введи версионированный манифест, например `project.shelter.json`: формат/версия, стабильный `projectId`, имя, версия игры, совместимая версия движка/SDK, стартовая сцена, список сцен, реестр ресурсов, подключённые модули и настройки сборки. Точные имена полей закрепи в схеме.

Проекты хранятся в обычных папках на диске. Отдели `scenes/`, `assets/`, `prefabs/`, `scripts/`, `settings/`, производный кэш и результаты сборок. Ссылки переносимы относительно корня проекта или разрешаются по стабильным ID. Абсолютные пути компьютера автора и временные URL не являются игровыми ссылками. Веб-интерфейс читает и сохраняет проект через локальную службу; localStorage/IndexedDB могут хранить вспомогательное состояние, но не являются единственным местом хранения авторских данных. Предусмотри переносимый архив проекта.

Документ сцены хранит общие сущности/компоненты и активную камеру, допускает пустую сцену, разные игровые модули и любое допустимое имя шаблона. Валидатор ядра не требует сооружения, героя или `BaseWorld`. Правила конкретного шаблона проверяет его модуль.

Настройки приложения, настройки проекта, авторские сцены, кэш ресурсов, восстановительные черновики, история сеанса и игровой прогресс имеют отдельные области хранения. Используй `projectId`, а для сцен — также `sceneId`; копирование проекта через «Создать копию» выдаёт новый ID, обычный перенос сохраняет идентичность. Отсутствующие/несовместимые модули объясняются пользователю; их данные не удаляются молча, запуск и сборка блокируются до разрешения ошибки.

Миграция формата создаёт восстанавливаемую копию и не разрушает исходник при сбое. Неизвестная более новая версия не интерпретируется как текущая. Проект можно перенести с ресурсами и кодом на другой компьютер, открыть в совместимом движке и заново собрать.

### 1.4. Как ИИ должен выполнять разработку

Начни с краткого отчёта о найденной технической основе и существующих возможностях. Для этого проекта зафиксируй Three.js как основу 3D и текущий TypeScript-код как основу игровых правил. Расширяй существующие инструменты выбора, манипуляторы, материалы и загрузку сцены; не создавай параллельный рендерер или вторую несовместимую систему сцен.

Разделяй общие средства редактора и данные/правила конкретной игры. Переиспользование Three.js совместимо с независимостью проектов: другая игра открывается с собственными сценами, ресурсами и модулями, сохраняя ту же техническую основу редактора. Подключение проектов на произвольных сторонних движках не является частью этой задачи.

Внутренние команды должны быть типизированными и проверяемыми. Правка группы объектов или планировки применяется целиком одной отменяемой операцией. Долгие импорт и сборка показывают прогресс, результат и возможность отмены. Внешняя правка файлов не затирает несохранённую сцену молча. Сохраняй читаемые форматы, стабильные ID и небольшие изменения файлов, чтобы разработчик или ИИ могли поддерживать код и проверять результат.

Автоматические тесты, диагностика и снимки нужны для проверки реализации. Они дополняют проверку реальных пользовательских действий в интерфейсе. Наличие только API, CLI, сгенерированного JSON или проходящего теста без работающих панелей не выполняет задачу. Полный CLI редактора, MCP-сервер и встроенный ИИ-чат не требуются.

### 1.5. Ручная работа без написания кода

Все типовые операции выполняются мышью, горячими клавишами и понятными панелями:

- Создать/открыть проект, создать сцену, выбрать стартовую сцену и сохранить работу.
- Найти модель или материал в общей библиотеке, посмотреть превью, добавить в проект и перетащить в сцену.
- Выделить объект или группу, переместить, повернуть, масштабировать, ввести точный размер, выровнять, скопировать и удалить.
- Изменить текстуры, материалы, свет, окружение, игровую камеру и доступные параметры готового игрового объекта.
- Построить или исправить комнаты, проходы, двери и лестницы с согласованным обновлением игровых границ и маршрутов.
- Назначить объекту готовое поведение из поддерживаемых проектом, выбрать связанные объекты и ресурсы через списки или щелчок в сцене. Технические ID и написание скрипта для этого не требуются.
- Запустить игру, остановить её, вернуться к правкам, отменить/повторить действие и собрать Web-игру кнопкой.

Схемы готовых компонентов должны задавать названия полей, единицы, значения по умолчанию, допустимые диапазоны и варианты выбора. Для игровых параметров показывай только то, что реально поддерживается подключённым модулем. Для смены модели или материала нельзя требовать ручной регистрации ресурса в исходниках; её выполняет импорт/библиотека.

Новый проект из шаблона уже содержит всё необходимое для пробного запуска. Пользователь может собрать простой уровень, использовать готовые возможности шаблона и получить Web-билд без создания TypeScript-компонента. Пока новой механики нет, она не появляется в интерфейсе как неработающая кнопка.

Имена и подсказки описывают результат действия. Ошибку можно найти и исправить в соответствующей панели или сцене; технические подробности доступны отдельно для диагностики. Сохрани игровые данные при ошибке и предоставь отмену. Инструкция пользователя должна показывать эти действия в интерфейсе, а документация программных расширений предназначена разработчику отдельно.

### 2. Рабочее пространство

Сделай плотный, читаемый интерфейс инструмента разработки: нейтральная тёмная тема, тонкие разделители, единый акцент выделения, аккуратные иконки, русские названия и подсказки с клавишами.

Компоновка по умолчанию:

- Сверху: меню «Файл», «Правка», «Вид», «Проект», «Сборка», «Окно», «Справка»; название проекта/сцены и признак несохранённых изменений.
- Основная панель: создание и открытие сцены, сохранение проекта, отмена/повтор, добавление объекта, «Играть», «Пауза/Продолжить», «Стоп», «Собрать игру».
- Центр: максимально просторное окно сцены с собственной компактной панелью инструментов.
- Справа сверху: **Сцена / Outliner**.
- Справа снизу: **Свойства / Details** с вкладками объекта, игровой камеры и окружения.
- Слева: сворачиваемая панель добавления объектов, открываемая по необходимости.
- Снизу: **Ресурсы / Content Browser**, доступные как закреплённая панель или временная выдвижная панель; вкладки «Ресурсы проекта» и «Библиотека движка».
- Нижняя строка: состояние сохранения, число выбранных объектов, доступ к журналу ошибок и предупреждений.

Панели можно скрывать, менять их размеры и переставлять в предусмотренные области рабочего пространства. Сохраняй расположение отдельно от документа сцены; добавь восстановление стандартной компоновки. На узком экране используй текущий принцип поочерёдных панелей, сохраняя доступ к сцене. Никакая панель не должна становиться недоступной после уменьшения окна.

Каждая отображаемая команда должна работать. Для временно недоступной команды укажи конкретную причину. Состояния загрузки, отсутствия выделения, пустой библиотеки и ошибок должны иметь понятное представление.

### 3. Окно сцены и управление

Добавь переключение перспективы, ортографических видов спереди/сверху/сбоку и рабочего вида 2.5D. Смена рабочего вида не меняет игровую камеру. Сохрани «Кадр игры», проверку форматов и направляющие композиции.

Предусмотри обычный освещённый вид, просмотр без освещения и каркас. Эти режимы изменяют только отображение редактора и корректно восстанавливают игровые материалы. Сетка, значки света и другие вспомогательные элементы включаются отдельно.

Управление:

- Q/W/E/R — выбор, перемещение, поворот, масштаб; F — фокус на выделении.
- ЛКМ выбирает, Shift/Ctrl/Cmd добавляют к выделению; рамка и выбор участника группы через Alt сохраняются.
- В перспективе ПКМ с WASD и Q/E перемещает рабочую камеру; клавиши инструментов в этот момент не срабатывают. Средняя кнопка панорамирует, колесо приближает. Орбитальное вращение вокруг фокуса доступно отдельным жестом; различай Alt+щелчок и Alt+перетаскивание.
- Контекстное меню коротким щелчком ПКМ отличается от перетаскивания камеры.
- Сохрани клавиши копирования, удаления, группировки, отмены, повтора, сохранения и изоляции. Покажи их в справке. Обрабатывай физические коды клавиш для русской раскладки.

Все горячие клавиши учитывают фокус: ввод текста, чисел и поиск не вызывают команды сцены. При потере фокуса сбрасывай нажатые клавиши и заверши или отмени активный жест предсказуемым образом. Учитывай системные сочетания macOS и браузера; у всех действий остаётся доступная кнопка.

Раздели включение и шаг привязок: перемещение в метрах, поворот в градусах, масштаб в процентах. Сохрани мировые/локальные оси. Добавь привязку к поверхности с отступом и необязательным выравниванием. В модуле 2.5D «На пол» ставит объект или композицию на выбранный этаж; в обычной 3D-сцене используй доступную поверхность без требования этажности.

Предпросмотр перемещения должен быть плавным. Один завершённый жест или серия правок одного числового поля создаёт одну операцию истории. Esc отменяет незавершённый жест. Заблокированный участник не допускает частичного изменения композиции.

### 4. Дерево объектов и свойства

Outliner синхронизирован с окном сцены: выделение, подсветка и прокрутка к выбранному объекту работают в обе стороны. Добавь поиск по имени, фильтры типов/категорий, переименование, контекстное меню и организационные папки. Сохрани текущие группы и операции над ними.

Разделяй папки организации, группы совместного редактирования и игровые связи. Перемещение в папку не меняет координаты и не превращает объект в дочерний трансформ. Полную систему наследуемых трансформаций и вложенных префабов в этот объём не включай.

Раздели временное скрытие в редакторе и сохраняемую игровую видимость. Существующее поле `visible` сохраняет прежний смысл для старых документов; «Скрыть в редакторе» и изоляция хранятся в рабочем состоянии. Блокировка редактирования остаётся явно обозначенной.

Инспектор показывает свойства по типу объекта и поддерживает поиск, сворачиваемые категории и сброс свойств к значениям по умолчанию. Сохрани положение, поворот, масштаб, размеры в метрах, настройки материалов, света, камеры и окружения. Различай размеры по локальным осям модели и габарит после поворота.

При нескольких выбранных объектах показывай общие свойства и состояние «Разные значения». Изменение одного поля не перезаписывает остальные различающиеся свойства. Сохрани независимость материалов экземпляров. Ошибочный ввод объясняй возле поля; рабочий документ остаётся валидным.

### 5. Ресурсы и хранение

Развивай текущую библиотеку: превью, название, тип, размеры, поиск, фильтры, папки и категории. Показывай ресурсы открытого проекта и явно подключённых общих пакетов. Мебель и текстуры текущего дома принадлежат While the light is on; в пустой проект они не попадают. Разделяй ресурс в библиотеке и его экземпляр в сцене. Перетаскивание показывает место установки и учитывает выбранный этаж/поверхность и привязки; Esc отменяет добавление. Сохрани PNG/JPEG/WebP и добавь импорт моделей из раздела 10.

Отдельно реализуй собственную общую библиотеку движка из раздела 5.1. Она доступна из менеджера проектов и редактора. В пустом проекте виден каталог доступного контента, но его файлы попадают в проект только при явном добавлении или выборе шаблона с этим контентом.

Поддержи сохранение выбранной композиции в пользовательскую библиотеку для повторного размещения. Новые экземпляры получают независимые ID; параметры и игровые привязки копируются по явным правилам. Композиция из декора не становится интерактивной автоматически. На первом этапе достаточно независимых копий без распространения последующих изменений шаблона на все экземпляры.

Сохраняй пользовательские ресурсы вместе с переносимыми данными проекта. Экспорт, импорт и повторное открытие не должны терять материалы и ссылки. Совместимость существующих `.scene.json` обязательна. Новую версию формата вводи только с явной миграцией; неизвестные обязательные ссылки показывай как ошибку.

Различай сохранённую сцену, текущие изменения и восстановительный черновик. Автосохранение черновика не снимает признак несохранённых изменений основной сцены. Неудачное сохранение и переполнение хранилища не показываются как успех. При открытии повреждённого файла текущая сцена остаётся целой.

Настройки панелей, камера редактора, фильтры и временная изоляция не входят в игровые данные. Старые сцены и ключи хранилища перенеси совместимым импортом именно в проект While the light is on. Новые проекты используют собственные области хранения. Если меняется способ хранения, миграция должна быть атомарной с сохранением исходных данных до успешного завершения.

### 5.1. Собственная библиотека движка по принципу Fab

Создай **Shelter Library** — общий каталог готовых 3D-моделей, текстур, материалов и наборов, доступный всем проектам. Fab служит ориентиром пользовательского процесса «найти → посмотреть → добавить в библиотеку/проект → использовать». В этой задаче реализуется собственная локальная библиотека со стартовым содержимым и импортом пакетов; коммерческий маркетплейс с аккаунтами, платежами и обязательным сервером не требуется. Прямое подключение к каталогу Fab не является условием работы.

Каталог содержит категории, теги, поиск по названию/описанию, фильтры по типу, стилю, формату, размеру ресурса и сложности модели, избранное и коллекции. Показывай состояния «доступен в библиотеке», «добавлен в проект», «есть другая версия». Карточки имеют реальные миниатюры; подробный просмотр модели позволяет вращать её, менять масштаб и освещение, а просмотр текстуры/материала — видеть повторение на плоскости и результат на тестовой форме.

У ресурса есть стабильный ID, версия, название, описание, категория/теги, автор и источник, сведения о лицензии/атрибуции, превью и зависимости. Для модели показывай размеры в метрах, число треугольников, материалы и объём файлов; для текстуры — разрешение, каналы, назначение и повторяемость. Материал связывает доступные карты Base Color, Normal, Roughness, Metalness и AO с правильными настройками цветового пространства и диапазонов. Не подменяй недостающие карты произвольными изображениями: используй документированные значения материала.

Библиотека должна быть непустой уже после установки: добавь нейтральный стартовый набор строительных элементов, мебели и реквизита, подходящий разным играм. Например: стены/полы, колонны, дверь/окно, лестничный модуль, стол, стул, стеллаж, шкаф, ящик, бочка и светильник; материалы дерева, металла, бетона, кирпича, штукатурки, ткани и земли. Это реальные пригодные к размещению модели и текстуры с корректным масштабом, геометрией и материалами, а не карточки-заглушки или одни примитивы. Для каждой заявленной категории поставь готовый пример. Модели библиотеки являются визуальными ресурсами; игровая дверь, лестница или источник света добавляют поведение через компоненты/модуль уровня.

Стартовый набор независим от While the light is on и доступен без сети. Фиксируй происхождение и условия использования поставляемых ресурсов. Пользователь может импортировать собственные GLB/glTF, текстуры и материальные наборы в общую библиотеку, изменить метаданные, собрать коллекцию и экспортировать/импортировать переносимый пакет с зависимостями. Отдельно храни оригиналы библиотеки, индекс/метаданные и восстанавливаемый кэш превью; пользовательские оригиналы не удаляются при очистке кэша.

«Добавить в проект» переносит выбранную версию ресурса и все зависимости в каталог проекта, регистрирует их в его реестре и фиксирует исходный ID/версию. Перетаскивание модели из общей библиотеки дополнительно создаёт экземпляр в сцене; перетаскивание материала на объект назначает его с возможностью отмены. Повторное добавление той же версии переиспользует уже добавленный ресурс. Изменение экземпляра или проектной копии не меняет общий оригинал и другие проекты.

Обновления библиотеки не меняют игры автоматически. Замена проектного ресурса новой версией выполняется явно, с проверкой зависимостей и возможностью восстановить прежнюю версию. После добавления контента проект открывается, переносится и собирается при недоступной общей библиотеке. Web-билд содержит только используемые ресурсы и необходимые зависимости; весь каталог движка в него не включается.

Сделай библиотеку удобной для ручной работы: пользователь ищет ресурс, сравнивает превью и характеристики, выбирает версию, нажимает «Добавить в проект» и перетаскивает объект или материал в сцену. Все необходимые фильтры и операции доступны в окне библиотеки. Внутренние индекс, импорт и операции назначения остаются типизированными и тестируемыми, но от пользователя не требуются API-запросы, ключ модели или правка списка ресурсов в коде.

Приёмка библиотеки: найти модель и материал через интерфейс; добавить одинаковую версию в два независимых проекта; изменить материал только в одном; пополнить библиотеку своим ресурсом; перенести один проект на чистое окружение без библиотеки; собрать и запустить Web-игру. Проверь сохранность зависимостей и атрибуции, отсутствие дубликатов при повторном добавлении и независимость проектов после обновления/удаления общей записи.

### 6. Игра внутри редактора

Реализуй явные состояния **Редактирование → Игра → Пауза → Стоп/Редактирование**.

«Играть» запускает актуальную сцену, включая ещё не сохранённые правки, внутри центральной области. Редактор остаётся открытым. Можно выбрать текущую или стартовую сцену проекта. Используются реальные runtime, модули, интерфейс и управление выбранной игры. Для While the light is on работают её герой, двери, предметы и освещение; пустая сцена запускается без них.

Пробный запуск получает отдельную копию авторских данных и отдельное игровое состояние. Он не читает и не изменяет обычный прогресс выбранного проекта по умолчанию и не записывает результат тестирования в основной документ или черновик. Это относится и к прежнему `shelter-base-v1`. Тестовые изменения отбрасываются при остановке.

«Пауза» останавливает симуляцию; «Продолжить» продолжает её. «Стоп» освобождает ресурсы пробного запуска и восстанавливает рабочую камеру, выделение, изоляцию, панели и историю. При ошибке старта редактор остаётся доступен, а причина показана в журнале.

Раздели маршрутизацию ввода между игрой и редактором. В игре клавиши выполняют действия, заданные проектом. В While the light is on Esc сохраняет семантику двери/паузы; остановка доступна отдельной кнопкой. Добавь явный способ вернуть фокус панелям. На паузе авторская сцена не редактируется случайно.

Существующий «Кадр игры» остаётся просмотром композиции без запуска симуляции. Дай пользователю ясно различать эти режимы.

Выдели из текущего `src/game.ts` управляемый жизненный цикл игрового сеанса с передачей контейнера, проекта, документа, реестра модулей и политики сохранений. Обеспечь корректную остановку кадрового цикла, обработчиков ввода, аудио и освобождение созданных GPU-ресурсов. Выбери интеграцию, которая повторно использует тот же runtime и проектные модули, что входят в готовую сборку, без конфликтующих глобальных обработчиков или DOM-элементов.

В первой реализации достаточно Play/Pause/Stop. Simulate, Eject и перенос изменений симуляции обратно в авторскую сцену остаются отдельными будущими задачами.

### 7. Архитектура и выполнение

Сохрани разделение на документ сцены, адаптер рендера/игры и интерфейс. Документ и команды должны проверяться без DOM/WebGL. Разделяй изменения документа и настройки рабочего пространства. Вынеси расширяемые панели и ввод из растущего `scene-editor.ts` в модули с понятной ответственностью; не создавай вторую параллельную систему сцен.

До реализации кратко опиши найденную техническую основу, зависимости и план этапов. Начни с выделения общих модулей из существующего кода на Three.js, формата проекта и совместимого переноса текущей игры. Затем сделай сквозной путь через интерфейс: менеджер проектов → создать/открыть → вручную разместить и настроить объекты → сохранить → проверить в игре → собрать Web-билд. Развивай рабочее пространство, дерево, инспекторы готовых компонентов, общую библиотеку со стартовым контентом, импорт моделей и инструменты планировки. Заверши проверкой двух проектов и полного ручного сценария без написания кода. После каждого этапа система должна оставаться работоспособной; технические API или внешний вид панелей не заменяют работающие пользовательские действия.

Учти текущие ограничения ресурсов: 2000 узлов, 24 встроенные текстуры, до шести активных источников с тенями, проверки размеров файлов. Не переноси лимиты встроенных в JSON картинок слепо на новый файловый каталог моделей: задай и документируй бюджеты отдельно для старого импорта, проекта, модели и runtime. Эти пределы не являются гарантией частоты кадров. Измеряй производительность на текущем доме и независимом проекте. Обновление одного поля не должно без необходимости пересоздавать всю сцену.

Не добавляй в этот объём Blueprint-подобный граф, редактор анимаций, Sequencer, Terrain/Foliage, моделирование полигонов, World Partition, многопользовательский облачный редактор, встроенный ИИ-чат, обязательные MCP/CLI-инструменты для редактирования сцен, настольные сборки игр и обязательный облачный сервис. Локальная служба файлов проектов и Web-сборки входит в выбранную архитектуру. Защити сохранения от потери при внешней правке файлов или открытии проекта в нескольких окнах.

### 8. Критерии готовности

Проверь пользовательские сценарии:

1. Старый документ открывается с прежними объектами, группами, материалами и игровой камерой.
2. Пользователь находит объект, выбирает его в дереве и сцене, меняет размер и материал; undo/redo восстанавливают результат.
3. Группа копируется с независимыми ID, перемещается и удаляется одной отменяемой операцией; блокировки соблюдаются.
4. Панели меняют размеры и сохраняют расположение после перезагрузки; сброс возвращает доступную компоновку.
5. Смена рабочих видов, скрытие, изоляция и каркас не меняют сохраняемые параметры игры.
6. Ресурс перетаскивается в сцену, композиция повторно размещается, экспортированный документ переносится без потери зависимостей.
7. «Играть» запускает несохранённую правку внутри редактора; взаимодействия работают, пауза останавливает время.
8. «Стоп» возвращает ровно прежнюю авторскую сцену и рабочее состояние; обычное игровое сохранение не изменилось.
9. Не менее десяти последовательных запусков/остановок не оставляют дополнительных кадровых циклов, обработчиков, звука или накапливающихся GPU-ресурсов.
10. Некорректный импорт, невалидное поле и отказ хранилища дают понятную ошибку без потери рабочей сцены.
11. Клавиши работают с русской раскладкой и не срабатывают при печати; интерфейс доступен мышью и клавиатурой.
12. Проверь компоновку при 1440×900, 1280×720 и текущем узком размере около 347×790, отсутствие горизонтального переполнения и перекрытых основных действий.

Выполни `npm test`, `npm run build`, `npm run test:e2e`; для изменённой загрузки ресурсов также `npm run build:pages` и проверку сборки с базовым путём Pages через существующий `test:deployment`. При разделении на пакеты обнови пути/команды и сохрани эквивалентное покрытие; проверки текущей игры должны запускаться для её проекта, а не навязывать её всем играм. Добавляй содержательные проверки новых сценариев и изоляции игрового сеанса. Сделай актуальные снимки редактора и пробного запуска; проверь ошибки браузера/выбранной оболочки. Если проверка недоступна, укажи точную причину.

Обнови документацию редактора и README по реально работающему поведению. Инструкция пользователя описывает запуск, создание/перенос проекта, расстановку и настройки, библиотеку, импорт, проверку и сборку через интерфейс. Отдельно документируй для разработчика техническую основу, контракты модулей и миграции. В итоговом отчёте перечисли сделанное, проверки и оставшиеся ограничения. Сборка выдаёт локальный результат; публикация сайта или магазина требует отдельного запроса. GDD текущей игры остаётся спецификацией этой игры и не становится ограничением всех проектов движка.

### 9. Обязательное создание игровых уровней

**Включено пользователем.** Реализуй как повторно используемый модуль конструирования 2.5D-уровней, доступный разным проектам. Он не является обязательным условием загрузки любой сцены движка.

Редактор должен визуально создавать и изменять сооружения, этажи, комнаты, стены/перекрытия, двери, окна/проломы, лестницы и точку появления персонажа. Из существующих `LevelDefinition` / `CompiledLevel` выдели общий контракт модуля. GDD используется для проверки перенесённой игры, а размеры, материалы, шаблоны и правила других проектов задаются их данными.

Сделай редактируемые семантические данные планировки единым источником для геометрии, препятствий, навигации, обзора и проёмов света. Перемещение отдельного меша стены не заменяет изменение комнаты или границы. Существующие архитектурные объекты должны получить стабильную связь с моделью планировки; сохранение и undo/redo восстанавливают её целиком.

Проверяй границы комнат, пересечения, концы лестниц, проёмы, достижимость точек и валидность появления героя. Ошибки выделяются в сцене. Незавершённый уровень можно сохранить как проект, но запуск невозможной планировки объясняет конкретные ошибки. Визуальное наличие окна или пролома само по себе не создаёт проход.

Минимальная приёмка: изменить границу комнат, дверь и лестницу; запустить игру и подтвердить совпадение видимой геометрии, маршрутов, блокировки движения, обзора и света; отменить изменение; экспортировать и восстановить уровень. Сохрани движение 2.5D и особенности лестничных проёмов/передних кромок перекрытий. Не добавляй новые игровые действия окон, крыши или лазания, пока их поведение отдельно не определено.

Инструменты модуля обязаны работать и в новом нейтральном 2.5D-проекте: построенная там планировка не содержит обязательных комнат, идентификаторов или ассетов исходного дома. В сцене без модуля доступно обычное размещение 3D-объектов, камеры и света.

### 10. Обязательный импорт собственных 3D-моделей

**Включено пользователем: статические GLB/glTF и пользовательские текстуры.**

Добавь импорт статических моделей с предпросмотром, размерами, настройкой единиц, размещением, материалами и текстурами. Для `.gltf` принимай связанные локальные файлы совместно и проверяй зависимости. Один GLB удобен как переносимый комплект. Поддерживаемые расширения glTF перечисли явно; неподдерживаемое содержимое даёт понятное сообщение.

Храни бинарные ресурсы отдельно от JSON документа, в каталоге выбранного проекта, по стабильным ссылкам. Импорт копирует ресурс и зависимости в проект; перемещение исходной модели вне проекта не ломает сцену. Переносимый экспорт включает используемые зависимости; повторный запуск не оставляет объекты со ссылками на исчезнувшие временные URL. Сохрани импорт старого формата сцен.

Проверяй размеры, геометрию, текстуры и доступный бюджет ресурсов до добавления в сцену. Удаление и замена освобождают ресурсы корректно, учитывая общие ссылки. Импортированный меш по умолчанию является декорацией; интерактивность и влияние на маршруты задаются отдельно.

Минимальная приёмка: импортировать модель с текстурами, добавить два независимых экземпляра, изменить материал одного, сохранить, перезагрузить и перенести экспорт в чистое хранилище. Оба экземпляра должны восстановиться, а материал второго остаться прежним. Повреждённые и неполные файлы не изменяют текущий проект.

FBX/OBJ и импорт скелетной анимации остаются будущими расширениями. Игровое поведение назначается пользователем из готовых компонентов проекта через инспектор. Новые типы поведения реализует ИИ/разработчик через контракт модулей; импорт модели сам по себе не создаёт игровую логику.

### 11. Сборка выбранной игры для Web

Добавь настоящую кнопку **«Собрать игру»**, окно настроек и журнал результата. Пользователь выбирает папку результата и запускает сборку без команд терминала или правки конфигурации. Внутренний pipeline использует выбранный проект и доступен автоматическим проверкам разработчика. Раздели сборку приложения редактора и сборку игры: запуск общей команды для репозитория с неизменным входным `src/game.ts` не выполняет это требование.

Настройки принадлежат проекту: название и версия игры, идентификатор приложения, стартовая сцена, включённые сцены, необходимые ресурсы/модули, цель `web`, режим Development/Release, выходное расположение и базовый путь размещения. Включай транзитивные зависимости сцен и явно объявленные динамически загружаемые ресурсы.

Процесс: сохранить текущие авторские данные проекта → проверить схемы, ресурсы, модули, планировки и стартовую сцену → скомпилировать код проекта и нужный runtime → подготовить ресурсы → собрать в отдельное временное расположение → проверить результат → выдать готовый билд. Если сохранение не удалось, сборка не продолжает работу со старой версией незаметно. Покажи этапы, прогресс, журнал, ошибки, отмену и итоговое расположение.

Каждая сборка использует зафиксированный снимок входных данных: дальнейшие правки не меняют уже начатую сборку. Прерывание или ошибка не уничтожают исходники и предыдущий успешный результат. Результат отделён от исходников/ресурсов проекта; предотвращай выбор опасного совпадающего выходного каталога. После успеха доступны «Показать результат» и «Запустить сборку».

В билд входят только игровой runtime, подключённые игровые модули и ресурсы выбранного проекта. Менеджер проектов, панели редактора, манипуляторы, черновики, соседние проекты и редакторские части модулей не поставляются. Готовая игра не требует установленного движка, исходного проекта, dev-сервера Vite или сохранений браузера автора. Сохраняй прогресс с идентичностью конкретного проекта/приложения.

Целевая сборка — **Web**. Выдавай переносимый каталог с `index.html` и необходимыми файлами и поддержи его упаковку в ZIP. Игра запускается через обычный статический HTTP-сервер. Проверяй корневой и вложенный путь, включая текущую публикацию Pages. Не обещай поддержку `file://` без отдельной реализации. Все обязательные ресурсы и runtime входят в результат; игра не обращается к локальной службе редактора, окружению разработки или внешним CDN для загрузки обязательных зависимостей.

В интерфейсе результат сборки показывает название проекта, версию, папку/архив, предупреждения и ошибки, кнопки «Открыть папку» и «Проверить сборку». Последняя запускает статический предпросмотр готового результата; пользователь не настраивает сервер вручную. Для диагностики сохраняй структурированный отчёт о входных данных, включённых сценах и файлах. Пробная игра редактора и проверка готового билда используют отдельные сеансы и корректно освобождаются при остановке.

Зафиксируй минимальные требования к браузеру/WebGL2 по фактической проверке. Оставь общие `ProjectStorage`, `ProjectSession`, `RuntimeSession` и `BuildService`, чтобы выбранная локальная оболочка не проникала в игровой runtime. Нативные игры Windows/macOS и установка отдельной оболочки редактора не являются этапом этой задачи.

### 12. Главная приёмка: два независимых проекта

Эти проверки дополняют сценарии раздела 8 и обязательны для завершения работы:

1. Запусти движок без открытого проекта. Менеджер доступен без загрузки кода и ресурсов While the light is on.
2. Открой перенесённую игру A. Проверь прежние сцены, камеру, взаимодействия, сохранения и новый редактор планировки.
3. Создай проект B из нейтрального шаблона в другом расположении. Через интерфейс добавь собственную GLB-модель, свет, камеру, вторую сцену и готовое поведение из шаблона. Настрой его поля в инспекторе. Не редактируй код или JSON проекта, ядра и редактора ради этого сценария.
4. Собери в B новую 2.5D-планировку с комнатами, дверью и лестницей; проверь движение, препятствия, обзор и свет. Отдельно проверь пустую 3D-сцену без требования этажа, дома и героя.
5. Сохрани, закрой и заново открой оба проекта. Перенеси B с ресурсами и кодом в другое расположение и открой через манифест/архив без старого списка недавних.
6. Переключай A/B: история, ресурсы, выделение, черновики и прогресс изолированы. Один и тот же локальный ID сцены или объекта в разных проектах не вызывает конфликтов.
7. Собери A и B по очереди из интерфейса. B не содержит ассетов/кода A, а A сохраняет свой контент. Проверь стартовую сцену и переход во вторую сцену B.
8. Запусти готовые результаты при закрытом редакторе и остановленной его локальной службе, без исходников проектов, с чистым пользовательским хранилищем и без dev-сервера. Используй только обычный статический сервер с готовым Web-билдом.
9. Проверь сборку B без доступного каталога A. Отсутствующий ресурс B, несовместимый модуль, ошибка кода или невалидная стартовая сцена дают конкретную ошибку и не создают ложный успешный билд.
10. Подтверди отсутствие прямых и транзитивных зависимостей ядра/редактора от игровой папки A. Зафиксируй архитектурную проверку импортов и состав игровых сборок.

Если переносимость, открытие другого проекта или самостоятельная сборка работают только для текущего дома, задача не завершена. В итоговых материалах приложи оба тестовых проекта, отчёт по проверенным браузерам и результаты их Web-сборки; ограничения среды укажи отдельно от реализованных возможностей.

### 13. Главная приёмка: человек корректирует игру без кода

Пройди следующий сценарий только через интерфейс редактора; автоматизированные браузерные проверки могут повторять те же действия:

1. Запусти редактор, создай проект из нейтрального шаблона и открой его сцену. Исходники, JSON и терминал для настройки проекта не открываются.
2. Найди модель и материал в общей библиотеке, посмотри превью, добавь в проект и размести в сцене. Импортируй ещё одну собственную GLB-модель через диалог файла.
3. Перемести и поверни модели, задай размеры в метрах, сгруппируй и скопируй композицию. Измени материал только у одного экземпляра; проверь undo/redo.
4. Построй простую планировку: комнаты, дверь и лестницу. Ошибочное соединение должно подсветиться с понятным объяснением; исправь его через визуальные инструменты.
5. Настрой свет, игровую камеру и доступное поведение готового объекта через инспектор. Связи с объектами и ресурсами выбираются из интерфейса, без вставки ID и написания кода.
6. Запусти игру, проверь соответствие расстановки, проходов и настроек; нажми «Стоп» и скорректируй сцену. Обычный игровой прогресс и авторская сцена не получают случайных изменений тестового запуска.
7. Сохрани проект, закрой и заново открой редактор. Проверь восстановление объектов, материалов, планировки и настроек.
8. Кнопкой «Собрать игру» выпусти Web-билд. Запусти результат через статический сервер при выключенном редакторе, без исходников и общей библиотеки; он должен содержать выбранные ресурсы и реальные изменения игры.
9. Внеси небольшую правку в перенесённую While the light is on тем же визуальным способом. Проверь, что для неё не потребовалось менять код проекта или движка и что второй проект не изменился.

Приложи краткую инструкцию пользователя, снимки ключевых панелей и результата, отчёт о проверках и готовые Web-сборки двух проектов. Если хотя бы одна обязательная операция доступна только через скрипт, JSON, CLI или внутренний API, пользовательский сценарий не завершён.
