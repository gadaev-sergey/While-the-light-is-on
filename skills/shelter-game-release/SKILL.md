# Игры Shelter Engine: довести до публикации

Рабочее пространство владельца: `/Users/gadaev/Documents/ChatGPT/2D GAME`. Если оно перемещено, найди корень по `package.json` с именем `shelter-base`, `src/engine/` и `games/`. Все команды ниже выполняются из корня движка. Сначала прочитай местные `AGENTS.md` и необходимые разделы `docs/engine/SDK.md`; игровая логика и ресурсы принадлежат своему проекту `games/<id>/`, а не редактору.

## Обязательный результат

По постоянному указанию владельца готовая игра, **играбельный прототип**, завершённая новая функция и исправление игровой ошибки должны появиться **и на GitHub Pages, и в каталоге Shelter Arcade**. Сборка на диске или исправленный код сами по себе не завершают такую задачу.

Публикация на собственном GitHub владельца и обновление каталога входят в этот согласованный процесс; не запрашивай повторное разрешение для каждого обычного выпуска. Явное ограничение в текущей задаче («не публикуй», «только локально», «сначала покажи») имеет приоритет. Соблюдай действующие ограничения доступа и подтверждения инструментов; не обходи их. Не переноси это разрешение на другие аккаунты, платформы или несвязанные проекты.

Не публикуй промежуточный нерабочий код, исследование, обзор без изменений, правки только документации или заготовку, в которую ещё нельзя играть. Изменения общего runtime требуют выпуска затронутых игр, а не всех примеров и черновиков подряд.

## Учёт разработки по токенам и моделям

В начале **каждого хода работы над конкретной игрой** (включая продолжение, исправление и проверку) выполни после создания папки проекта:

```sh
npm run usage:begin -- games/<id>
```

Команда берёт `CODEX_THREAD_ID` (в Claude Code — `CLAUDE_CODE_SESSION_ID`), привязывает только текущий ход чата и учитывает его с начала. Перед финальным отчётом выполни `npm run usage:sync -- games/<id>`. Повторные вызовы не удваивают расход. Каждый следующий ход нужно привязать отдельно, даже в том же чате. Если для этой игры уже работают явно разрешённые пользователем агенты, привяжи их ходы тем же способом; само правило учёта не требует создавать агентов.

Не приписывай одной игре весь общий чат, разработку движка/каталога или работу над другой игрой. Один ход относится к одной игре: для независимой работы над другой игрой нужен отдельный ход. Для восстановления подтверждённой старой разработки используй `--thread UUID --turn UUID`; сначала установи, к какой игре относится этот ход. Не используй случайно выбранный последний чат.

Фактический источник — локальные `token_usage_record` Codex или записи `usage` журнала Claude Code; названия моделей берутся из метаданных хода или самой записи. Храни только счётчики и ссылки на источник в `games/<id>/settings/ai-usage.json`. Тексты чатов, инструменты, рассуждения и секреты в статистику не копируются. Служебные чаты автоматического согласования отдельно к игре не относить. Если формат не поддерживается или данных нет, сообщи «расход не зафиксирован», а не 0 и не оценку по длине ответа.

Всего токенов = вход + выход, включая вход из кэша. Кэш уже входит во вход, рассуждения — в выход; повторно их не прибавлять. Проценты моделей считаются от общего числа учтённых токенов, это не проценты авторства кода и не стоимость в деньгах. Общий контекст движка, попавший во входящий запрос при работе над игрой, учитывается как часть этого запроса.

Редактор: **Проект → ИИ · статистика разработки**, обновление каждые 5 секунд при открытом окне. Каталог получает публичный снимок агрегированных чисел при `publish:catalog` / `release:game`; внутренние ID чатов и пути журналов не публикуются. Последний ответ хода может попасть в журнал уже после выпуска — следующая синхронизация подхватит его. Подробности и ограничения: `docs/engine/AI-USAGE.md`.

## Перед выпуском

1. Доведи заявленную работу до проверяемого игрового результата. Проверь старт, ключевое управление и изменённое поведение; запускай подходящие тесты из `tests/<id>/`. Для исправлений общих модулей проверь затронутые сценарии движка. Выполни `npx tsc --noEmit`.
2. Для изменения уже опубликованной игры увеличь `gameVersion`: исправления — patch, совместимые новые функции — minor, несовместимые изменения — major. Не меняй `projectId` и `build.appId` у обновления существующей игры: это сбрасывает её идентичность и прогресс. Сохраняй прежний публичный адрес.
3. Для новой игры добавь карточку в `catalog/games.json` с уникальными `id`, `project`, `projectId`, своим `repository` и его `url`, названием, жанром, кратким фактическим описанием и реальным кадром игрового процесса. Сначала установи `published: false`; такой черновик не попадёт на сайт. Играбельную незавершённую игру обозначай `status: "prototype"`, законченную — `"release"`.
4. Для патча обнови описание и признаки карточки, если они изменились; замени превью, если прежний кадр больше не представляет актуальную игру. Снимок должен показывать саму игру без окон редактора, ошибок и отладочных панелей. Сохраняй его в `catalog/assets/` как JPEG, PNG или WebP. Не подменяй игровой кадр вымышленной иллюстрацией.

## Выпуск игры и каталога

```sh
npm run release:game -- games/<id>
```

Команда проверяет карточку, собирает игру в Release с относительными путями, при необходимости создаёт отдельный публичный репозиторий в аккаунте владельца, отправляет только готовую игру в `gh-pages` и ждёт успешного развёртывания **этого коммита**. Затем отмечает карточку опубликованной, записывает версию, дату и SHA, собирает и публикует каталог. Она не коммитит весь рабочий каталог движка.

Если изменилась только карточка или оформление каталога, либо игра уже опубликована, а обновление каталога не завершилось:

```sh
npm run build:catalog
npm run publish:catalog
```

Не правь выпущенный HTML вместо исходного реестра. Не добавляй вторую карточку вместо обновления существующей. Не объявляй прототип полной игрой только потому, что сборка прошла.

## Проверить именно публичный результат

- Дождись подтверждённого развёртывания игры и каталога. Один `git push` не означает, что сайт готов. Последняя успешная сборка от старого SHA тоже не подтверждает новый выпуск.
- Открой публичный URL игры в браузере, проверь загрузку скриптов и ресурсов, запуск, изменённое поведение и отсутствие ошибок. Для игр с сенсорным управлением проверь мобильный экран.
- Открой публичный каталог: правильная карточка, описание, превью, версия, дата и рабочий переход к игре. При выпуске нескольких игр проверь каждую.
- Дай пользователю ссылки на игру и каталог. Сообщай, что опубликовано, только после подтверждения обоих этапов. Не выдавай локальный предпросмотр за публичный сайт.

## Доступ и восстановление

Используй существующие Git HTTPS credentials, GitHub CLI или `GH_TOKEN` / `GITHUB_TOKEN` через штатный модуль. Не выводи и не записывай токены в файлы, карточки, логи, аргументы команд или исходники. Для новой публикации аккаунт должен иметь нужные права на репозиторий, Contents и настройку Pages.

Не перезаписывай чужую ветку `gh-pages`, не используй force-push и не меняй видимость существующего репозитория. Маркер `.shelter-publish.json` защищает ветку другой игры. При конфликте выбери корректный репозиторий, а не снимай защиту.

После неоднозначного ответа GitHub сначала прочитай состояние. `configurePages` уже учитывает случай, когда отправка `gh-pages` включила Pages до запроса API. Не создавай новый репозиторий и не загружай ту же игру повторно только из-за временной ошибки. Для ожидания используй ограничение штатного издателя; при тайм-ауте проверь Actions и SHA. Если нужны права или действие владельца, сохрани сборку, назови конкретную причину и честно перечисли, что уже опубликовано и что осталось. Не помечай всю задачу завершённой при неработающей игре или отсутствующей карточке.
